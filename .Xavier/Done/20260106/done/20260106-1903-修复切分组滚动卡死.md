# 修复切分组滚动卡死

## 概述
当前现象：切换分组后立刻快速滚动笔记列表，界面出现明显卡顿/假死（主线程响应变差）。
初步判断为：分组切换触发了笔记列表的过滤计算与 SwiftUI 视图刷新；过滤任务被放到 `DispatchQueue.global(qos: .userInteractive)`（最高优先级）执行，在数据量较大时会与 UI 主线程争抢 CPU，导致滚动期间主线程得不到足够时间片，从而表现为“卡死”。

## 流程图
```mermaid
flowchart TD
  A[用户切换分组] --> B[onChange(selectedGroupId)]
  B --> C[updateCachedNotes]
  C --> D[后台线程过滤 notesIndexSnapshot]
  D --> E[回到主线程更新 cachedFilteredNotes]
  A2[用户快速滚动列表] --> F[主线程需要持续处理滚动/布局]
  D -->|qos: userInteractive 抢占CPU| F
  F --> G[UI 卡顿/假死]
```

## 方案
### 方案A（推荐）：降低后台过滤任务优先级 + 支持取消/只提交最新结果
- 将过滤任务从 `DispatchQueue.global(qos: .userInteractive)` 改为更合适的优先级（例如 `.utility` / `.userInitiated`），避免与 UI 主线程抢占资源。
- 增加“取消上一次过滤 / 只应用最新一次过滤结果”的机制：
  - 分组快速切换、搜索文本变化时，不累积高优先级任务；旧任务直接取消。
  - 过滤完成回到主线程前，校验是否仍是最新请求，避免旧结果覆盖新状态。

优点：
- 直接针对“滚动期间卡死”的资源争抢根因；
- 代码改动小，风险可控；
- 同时改善分组/搜索快速切换时的体验。

缺点：
- 需要一点点并发控制代码（Task/取消/版本号）。

### 方案B：完全在主线程同步过滤
优点：实现简单。
缺点：数据量大时更容易直接卡死主线程，不推荐。

3. 预期：滚动保持流畅，窗口不再出现“卡死/无响应”。

## 任务总结与结论
通过降低后台过滤任务优先级并加入可取消/只提交最新结果的缓存刷新机制，避免分组切换后的高优先级计算与 UI 线程争抢资源，修复“切分组后快速滚动卡死”。
