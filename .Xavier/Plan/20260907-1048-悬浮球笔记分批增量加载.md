# 方案分析：悬浮球笔记分批增量加载

## 1. 需求说明
- **需求目标**：将悬浮球附带的笔记列表（`NoteListView`）从一次性全量渲染改为**分批增量加载**（Pagination / Incremental Batch Loading）。
- **优化目的**：避免在笔记条目数量较多时，因瞬间加载与测量过多的复杂笔记卡片（包含 Markdown、高亮、操作菜单及自适应高度等）引发主线程卡顿、掉帧或首开延迟，提升列表滑动与窗口打开的流畅度。

---

## 2. 现状排查与根因分析

### 2.1 现状与性能瓶颈排查
1. **全量计算与渲染**：
   在 `Sources/View/NoteListView.swift` 中，`filteredNotes` 会根据当前模式、分组与搜索词一次性全量过滤出所有匹配的 `Note`：
   ```swift
   ForEach(filteredNotes) { note in
       if note.isAI {
           AINoteItemView(...)
       } else {
           NoteItemView(...)
       }
   }
   ```
2. **测量与布局开销**：
   悬浮球窗口为了实现高度随内容自适应，在 `NoteWindow.swift` 中调用了 `hostingView.fittingSize`，并在 `NoteListView` 中使用了 `preference(key: ViewSizeKey.self)`。
   当包含上百条笔记时，为了计算整体理想尺寸，SwiftUI 会提前实例化并测量列表中的所有 `NoteItemView`，产生密集的 CPU 占用和重排开销，造成展开与滚动时的卡顿。

### 2.2 解决方案设计
1. **定义分页常数与加载状态**：
   - 批次大小：`pageSize = 20`（第一批加载前 20 条，后续每次增量加载 20 条）。
   - 状态追踪：`@State private var displayedCount: Int = 20`。
   - 视口切片：`visibleNotes: [Note] { Array(filteredNotes.prefix(displayedCount)) }`。
   - 是否还有未加载项：`hasMoreNotes: Bool { displayedCount < filteredNotes.count }`。
2. **增量触发机制（双重触发）**：
   - **触底预加载**：渲染项到达倒数第 3 条时，通过 `.onAppear` 自动预加载下一批，实现无感知顺滑加载。
   - **底部加载指示器**：列表末尾若存在未加载项，显示轻量加载提示并支持触底自动拉取下一批，避免一次性把所有视图挂载到视图树。
3. **状态智能重置**：
   - 当用户切换模式（`viewMode`）、切换分组（`selectedGroupId`）、修改搜索关键字（`searchText`）时，自动将 `displayedCount` 重置为 `pageSize`。
   - 当用户新增笔记时，若处于当前分组，确保新笔记位于最前面且 `displayedCount` 自动容纳新笔记。
4. **与高度自适应的无缝协同**：
   - 依赖 `visibleNotes` 动态变化，通过既有的 `ViewSizeKey` 自然响应并刷新高度，首屏只需测量 20 条，极大幅度降低测量与渲染消耗。

## 4. 循环评审设计 (Review Design)
- **核心关注点**：
  1. 笔记窗口初次打开与展开时是否明显更加轻快、无卡顿；
  2. 向下滑动到底部时能否顺畅自动增量加载出后续笔记；
  3. 切换分组、切换分类模式（如闪念/已完成/智库）及搜索时，是否正常从第一批开始展示。
- **评审方式**：通过 `ask_question` 发起评审，等待用户明确批准后进入代码实施。
