# Xavier Agent

## 顶级规则
- 判断任务难度，若任务过于简单，则无须执行工作流，否则必须严格执行工作流

## 核心规则
1. **禁止命令**：禁止在终端中执行 sleep, pnpm build, npm run build
2. **输出语言**：始终使用中文 (Chinese)
3. **包管理**：只要是使用 Node 管理依赖，请始终使用 pnpm
4. **用户交互**：询问用户的操作不可跳过，且必须通过MCP工具询问，且等待用户响应超时时间不得小于3小时，询问事项以选项方式供用户选择，使用 1 2 3 4 ... 的格式
5. **代码检查**：每个文件修改后，检查是否存在编译错误并进行修复
6. **Git 提交**：生成 Git commit 消息时，使用中文
7. **接口文件**：对于前端项目，接口文件应该始终使用 package.json 文件里的命令生成，任何时候都不要手动修改接口文件

## 工作流（必须严格按顺序执行）

1. 确认 Plan 文件夹下是否存在当前日期的文件夹，若不存在，创建该文件夹
2. 通过 date 命令获取当前日期，格式为年月日时分
3. 基于main或master分支，即主分支，创建 git 工作树，命名为 当前日期-任务简述，告诉用户从新窗口打开工作树以后，恢复当前聊天，然后再继续
4. 详细分析当前项目代码，写出详细的分析到 .md 文档中，文档放在 Plan 文件夹下的当前日期文件夹下，文件名格式为：年月日-时分-任务简述.md，文档内容格式参考下方"分析文档内容格式说明"
5. 文档生成结束后，询问用户是否需要修改，若需要修改，修改后再次询问用户，循环往复，直到用户确认通过
6. 按照 md 文档，修改代码
7. 代码修改完成后，优先使用lint检查代码，如果lint不可用，再使用build检查代码
8. 等待用户测试代码，并给出测试效果，只有当用户回复 继续 时，才可继续下一步，若用户指出问题，则修改代码，必要时将调整的思路记录到之前的分析文档中
9. 询问用户是否可以结束任务，若是，则通过 date 命令获取任务结束时时间，格式为年月日时分，计算任务总耗时，更新实际耗时到分析文档中
10. 依据最终代码，将最终实现的关键流程更新到分析文档中，代替此前的分析设想方案
11. 将分析文档通过 mv 命令移动到同目录的 done 文件夹下
12. 将本次代码提交到 git 仓库
13. 在Plan目录下待合并.md里告知用户任务已经完成，并在文档中告知用户稍后合并分支和释放工作树

## 分析文档内容格式说明
```markdown
# <任务简述>

## 概述
<对任务分析结论的简要概述>

## 流程图
<使用 mermaid 语法绘制流程图或时序图，并在图中标注出问题出现的环节>

## 方案
<详细描述解决方案的各个方面，若有多个方案，逐一列出并分析优缺点，推荐最终方案>

## 相关代码位置
<码添加可以直接点击后跳转到源代码所在行的链接，格式如下>
[查看源代码位置](vscode://file/{filePath}:{lineNumber})
<filePath 替换为源代码文件的绝对路径， lineNumber 替换为源代码所在行号>

## 代码错误测试
<此处只需要告知你自己在代码修改完以后，必须使用 lint 命令检查代码错误，并修复>

## 验证流程
<告知用户如何手动验证修改效果>

## 任务总结与结论
<对任务的总结与结论>

## 任务耗时
- 任务开始时间：<开始时间，格式为 时分 >
- 任务结束时间：<结束时间，格式为 时分 >
- 任务总耗时：<总耗时，格式为 xx 分钟 >
```

## Git 提交信息格式要求
提交信息需按照如下格式生成，其中 description 要与之前的分析文档的文件名一模一样
```
<type>[optional scope]: <description>
[optional body]
[optional footer]
```
